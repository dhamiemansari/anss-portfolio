The design system came before the first screen

A token-first design system for a six-module enterprise HRMS — built solo in under a week with an AI agent, and now used in both design and development.

First, a little context

About the client

An Indian enterprise (under NDA) building an HRMS: one platform for employees, policies, payroll-adjacent masters, settings and super-admin controls. It was planned as a large product that would keep growing, module by module.

Overview

Before any screen was designed, I built the design system on my own. Three designers then designed the platform on top of it, and the development team built the same components in code.

KEY POINT

On a platform this big, inconsistency compounds. Every screen drawn without a system is a screen someone redraws later — so the system had to come first.

The system had one job: let several people build a large product in parallel without it drifting apart

CORE PROBLEM STATEMENT

“A team of three designers is building a six-module enterprise HRMS. They need one shared set of tokens and components, so they can ship every module looking and behaving the same.”

Written as a user story — user, role, need and goal — before any component was drawn.

Developers needed the same thing from the other side: component names and states that match what they build.

Four demands shaped what the system had to cover

Looking at the platform’s first modules, these four set the scope of the system.

01

Six modules, three designers

Login, employee management, policies, settings, masters and super admin — designed in parallel.

02

Data-heavy screens

Tables, filters, bulk upload and row actions appear on almost every page.

03

Light and dark from day one

The theme layer carries both modes, so no component hard-codes a colour.

04

Built in code too

Developers implement the same components, so names and states had to match.

Three rules kept a fast build from turning into a messy one

Speed came from the AI agent. These rules made sure speed didn’t cost consistency.

01

Theme before components

Tokens first, so every component — and every AI-generated variant — is on-brand from the first run.

02

Borrow structure, own the brand

Component anatomy comes from a proven open-source kit; the look comes entirely from the client’s theme.

03

Every change is versioned

A changelog with semantic versions, so designers and developers always know what moved.

Breaking down the build, step by step

Theme first, then the agent, then the rules for changing it.

1. The theme came first, built by hand

  • Problem identified: Components built before tokens end up full of raw values that drift module by module.
  • What I did: Set the tokens in three layers — a base scale, a theme layer with light and dark modes, and a full colour palette — with typography, shadows and spacing set the same way.
  • Why it mattered: Nothing downstream would ever need a raw value.

2. Components were built with an AI agent — and judged by me

  • What the agent did: Generated component frames, variants and states through Figma’s MCP connection, applied theme tokens and text styles to every layer, and repeated the pattern across all 28 components.
  • What I did: Built the theme and the naming before any component, chose which components and states the platform needed, and reviewed every component, fixing what didn’t hold up.
  • Why the order mattered: Because the theme came first, the agent never had to guess a colour or a font. Its output was on-brand from the first run — my time went into judgement, not pixel-pushing.

3. A changelog the whole team writes in

  • Problem identified: Once three designers and a development team depend on a system, an unannounced change is a bug.
  • What I did: Added a changelog page with semantic versions and a status legend — added, changed, deprecated, removed, fixed.
  • Where it landed: Every entry names who made it, so a fix in one place never silently breaks another.

The client doesn’t share product metrics, so I measure this by what the system made possible:

  • The system existed before the first screen — nothing had to be redesigned to fit it later.
  • Three designers built the platform’s modules from the same components and tokens.
  • The development team built the same components in code, with matching names and states.
  • Changes are versioned, so a fix in one place doesn’t silently break another.

What I would do differently next time

Working with an AI agent changed where my time went. The slow part of a design system used to be drawing every state; here it was deciding what the system should be — the theme, the naming, the components the product actually needed.

Write the decisions down next to the components. Next, I’d add usage guidelines to each component — when to use it, and when not to — and finish the five components still paused. A system is only as consistent as the decisions written down next to it.
